# Flower 기반 ASR·모듈러 집계·비공개 MGF 설계 계약

2026-10-08: 현재 사용자는 [동일 스케일·단일 벡터 목표](same-scale-asr-goal.md)를
지정했다. 아래 분리 집계+ZKP 계약은 이전 설계 기록이며 현재 실행의 필수
선행 조건으로 취급하지 않는다. 새 목표에서 필요성이 확인되기 전에 ZKP를
구현하거나 기존 벡터를 두 경로로 분리하지 않는다.

작성/재검토: 2026-10-06. 상태: **ASR 참여 정책은 CCS/VRF까지, 다중 라운드 누출 검사는 보류**.
이 문서는 수치 기준 구현에 들어가기 전에 지켜야 할 계약이다. 안전한 HPRF나
전체 프로토콜을 구현 완료했다는 보고서가 아니다. 기존 원본 재현 경로는 보존한다.

[실현 가능성 재검토와 단계별 계획](reproduction/asr-plan-feasibility-2026-10-06.md)을
함께 따른다. 사용자 범위 축소에 따라 공개 이력 rank 검사, all-or-none 그룹 처리,
그에 따른 그룹 재편·독립 키 재공유는 이번 구현·완료 조건에서 제외한다.
§2.1–2.3은 과거 보강 후보를 보존한 참고 기록이다. 실제 BLMR·VSS·ZKP 비용과
CCS 등록·난수 조건은 여전히 확인해야 하며 전체 구현 가능성이나 완료 시간을 단정하지 않는다.

## 1. 범위와 공통 복원식

ASR과 Flower 메시지 전달을 유지한다. AMR이나 외부 P2P로 전환하지 않는다.
개별 평문 업데이트, MGF 검사 벡터, 좌표별 carry, 추가 라운드별 mask share는
공개하지 않는다. 키는 task 초기 한 번 공유해 재사용한다. 누출 검사에 따른
그룹 키 재등록·재공유는 이번 범위 밖이다. 따라서 CCS/VRF를 사용해도 MGF나
이탈로 공개 명단이 달라질 때 개인 키가 노출될 수 있다는 한계가 남는다.

원본의 scalar HPRF는 비교용으로만 보존한다. 새 HPRF는 BLMR 계열의 정확한
구성과 파라미터를 선정한 뒤 회로를 만든다. 직접 update norm 검사로 원본
masked-MGF를 조용히 대체하지 않는다. 초기 bound는 공개 설정값으로 시작하고,
후속 이력은 Algorithm 6의 `H(K_A, input)` 기반 통계량으로 정의한다.
이를 실제 정수 마스크 합 `sum(h_i)`와 동일시하지 않는다. 원본 percentile
초기화 및 실제 mask-SUM norm을 쓰는 artifact와의 차이는 별도 실험 항목이다.

모든 벡터 식은 좌표별 연산이다. `n_i`는 사전 승인된 데이터 가중치다.

```text
z_i = round(S * x_i)
h_i = H(k_i, Encode(round, block))
C_i = (Delta * n_i * z_i + h_i) mod p
private MGF: ||z_i / S + alpha_r * h_i||_2 <= b_r

K_A = (sum_{i in A} k_i) mod q       # ASR 복원 후 HPRF 키 공간으로 변환
R = center_p((sum_{i in A} C_i - H(K_A, Encode(round, block))) mod p)
Z_A = round(R / Delta)              # 정확한 양자화 가중합 sum(n_i * z_i)
FedAvg = Z_A / (S * sum_{i in A} n_i)
```

`center_p`는 잔여값을 `[-p/2, p/2)`의 정수 대표로 옮긴다. 모듈러 뺄셈이
mask carry를 없애고, center가 음수를 복원하고, 반올림이 작은 HPRF 오차를
제거한다. 마지막 나눗셈은 일반 유리수/실수 연산이지 체의 역원 연산이 아니다.
MGF 검사 좌표가 일부여도 HPRF·전송값 결속과 update 범위 검사는 전체 좌표에
적용한다. 총합/평균 단위와 가중/비가중 MGF 이력은 manifest에서 구분한다.
첫 논문 비교는 동일 가중치를 사용하고, 일반 가중 이력은 명시적 확장으로 둔다.

## 2. 현재 참여 정책: CCS/VRF, 누출 대응 보강은 보류

### 2.0 CCS/VRF와 실제 공개 명단을 구분

논문 CCS의 VRF 기반 초기 subset 배정과 제출 증명 검증까지 구현한다. VRF는
배정의 검증 장치이며 MGF/dropout 이후 달라진 실제 명단의 키 합 누출을 자동으로
막지 않는다. 사용자 결정에 따라 §2.1의 공개 이력 검사는 이번에 구현하지 않는다.
세부 등록·난수 조건과 수정 순서는 [재검토 §5–6](reproduction/asr-plan-feasibility-2026-10-06.md)을 따른다.

현재 흐름은 `CCS 참여 자격/VRF 검증 → MGF·ZKP·범위·가중치 검증 → 통과 명단의
BFT① 확정 → 해당 명단의 ASR → 모듈러 복원 → 결과 BFT②`다. CCS subset 안에서
개별 통과자를 선택하며, 한 명 탈락을 이유로 그룹 전체를 제외하지 않는다.
승인 최소 인원·VSS 정족수·집계 용량 조건이 부족하면 집계를 거부한다. 이 조건을
만족해도 다중 라운드 키 누출 안전성을 보장한다는 뜻은 아니다.

VSS share 검증, 클라이언트 서명, 실제 ZKP 검증, BFT 확정 명단과 key release의
결속, 동일 round의 상충 명단/재시도 방지는 유지한다. 이 기본 검증을 생략하거나
기존 검증을 끄는 요청으로 해석하지 않는다. 과거 공개 명단의 선형 관계에 따른
차단만 보류한다. 결과에는 해당 보강 미구현과 잔여 누출 위험을 명시한다.

BLMR 벡터 키/Pedersen commitment를 표준 ECVRF 키로 그대로 사용할 수 없으므로
별도 VRF 키를 초기 client 등록에 결속하는 안을 검토한다. seed 공개 전 등록 고정,
공개키 검증, seed 편향 방지, 배정 공개 시점을 명시해야 한다. 현재 BFT의 개별
서명 목록은 유일한 threshold signature가 아니므로 그 hash만으로 안전한 난수
원천이 구현됐다고 표시하지 않는다. 고정 seed는 기능 시험에만 사용한다.

### 2.1 공개 이력과 검사 기준 — 보류한 보강안

이 절과 §2.2–2.3의 절차·필수 표현은 해당 보강안을 채택할 경우의 계약이며,
현재 CCS/VRF 범위의 선행 작업이나 완료 조건이 아니다.

ledger의 열은 `(task_id, client_id, key_epoch)`이고, 행은 복구 가능하도록
내보낸 키 합의 0/1 선택 벡터다. 가중치는 update에만 곱하므로 키 합의 계수는
`n_i`가 아니라 1이다. 키 좌표마다 같은 선택 행렬을 적용한다.

이력 행렬을 `B`, 후보 명단의 행을 `a`, `B_new = [B; a]`라고 한다.
VSS 체 `F_ell`에서 어떤 보호 대상 키의 단위벡터 `e_i`에 대해

```text
e_i in rowspan(B_new)
<=> rank(B_new) == rank([B_new; e_i])
```

이면 그 후보를 공개하지 않는다. 단순히 rank 증가나 full rank만 검사하지 않는다.
`{1,2}`, `{1,2,3}`의 두 합만으로도 세 번째 키가 복원된다. `{1,2}`, `{2,3}`,
`{1,3}`의 세 합도 홀수 특성의 체에서는 개별 키를 모두 드러낸다.

알려진 공모 키는 해당 열의 기여를 제거한 뒤 검사한다. 알 수 없는 공모 집합의
최대 크기 `t_collude`를 위협 모델에 선언한다. 모든 공모 부분집합 검사는
조합적으로 비싸질 수 있으므로 "rank 검사 한 번이면 모든 공모에 안전"이라고
표시하지 않는다. 아래의 고정 그룹 불변식을 이용한 보수적 검사도 허용하되,
해당 공모 가정과 적용 가능한 이력을 명시해야 한다.

이 검사는 **공개된 선형 키 합에서의 직접 키 복원 차단**이다. 작은 키 범위,
비선형 보조정보, 향후 무제한 키 탈취까지 포함한 비공개성 증명은 아니다.
sum이 외부 로그에는 없어도 어느 aggregator가 복원할 수 있으면 공개 이력이다.
기존 이력만으로 이미 복원 가능한 키는 노출 상태로 기록하고 재사용을 중지한다.
그 열을 알려진 키로 처리해 다른 키에 미치는 영향도 검사하며, ledger에서 지워
새 후보를 안전해 보이게 만들지 않는다. 해당 그룹의 복구에는 §2.3을 적용한다.

### 2.2 고정 그룹 단위의 부분 진행 — 보류한 비교 후보

이 절은 구현 가능한 보수적 절차를 정의하지만 채택 승인은 아직 아니다. 균등
고정 그룹·악성 20% 전원 탈락이라는 예에서는 그룹 크기 10일 때 예약 100명 중
남는 인원 기댓값이 약 10.5명이다. §2.0의 CCS를 붙여도 이 가용성 문제는 남는다.
개별 필터링+누출 검사 및 최초 통과 명단 고정/독립 키 재등록 후보와 비교한다.

그룹은 key epoch 시작 전에 manifest로 고정한다. 같은 그룹의 현재 키들은
언제나 함께 포함하거나 함께 제외한다. 권장 불변식은 누적 공모 상한 아래에서
각 유효 그룹에 최소 두 개의 비공모 키가 남는 것이다. 전역 공모 상한만 아는
경우 그룹 크기 `>= t_collude + 2`는 그 목적의 충분조건이며, 단순히 그룹
크기가 2라는 이유만으로 공모에 안전한 것은 아니다.

이 비교 후보를 시험할 때의 명단 선정 절차는 다음과 같이 고정한다.

1. 증명, 승인 가중치, 초기 VSS 등록, 제출 시한을 확인한 개별 통과 집합을 만든다.
2. 멤버 전원이 통과한 그룹만 후보로 둔다. 일부가 빠진 그룹은 이번 round에서 제외한다.
3. 후보 그룹을 manifest의 고정 순서로 처리한다. 빈 후보 명단에서 시작해
   그룹 하나를 추가한 전체 명단에 §2.1 검사를 수행한다. 위험하면 그 그룹의
   추가를 거부하고 다음 그룹을 검토한다. 중간 명단의 share는 공개하지 않는다.
4. 최종 명단에 대해 누출·공모 정책, 최소 인원/가중치, 최대 용량을 다시 검사한다.
5. BFT①가 최종 명단·vector digest·가중치·key epoch·ledger 버전을 확정한 뒤에만
   해당 명단의 aggregate key share를 내보낸다.

위 절차는 안전한 부분 진행을 시도하는 결정적·보수적 정책이다. 누출 위험은
그룹 조합과 이력에 의존하므로 유일한 "문제 그룹"이 항상 존재하지 않는다.
이 greedy 절차가 가능한 최대 명단을 찾거나 모든 가능한 안전한 조합을 찾는다는
보장도 없다. 마지막 조건을 만족하는 명단이 없으면 **키 공개 없이 그 round를
건너뛴다**. 기존 모델/이력은 유지하며 임계값을 완화해 탈락자를 채우지 않는다.

집계자들의 aggregate-share 발급 전 검사는 필수다. coordinator 한 곳에서
검사하는 것으로 대체하지 않는다. 승인 이력을 먼저 영속화하고, share가 나간
뒤 모델 BFT②가 실패해도 ledger 행을 삭제하지 않는다. 서로 다른 coordinator,
view-change, 재시작, 보류 중 요청을 통해 병렬 subset 공개가 우회되지 않게 한다.
같은 round의 재시도는 같은 확정 명단과 같은 ciphertext만 허용한다.

### 2.3 반복 방해와 그룹 복구 — 보류한 보강안

그룹 격리 기준, 관측 창, 영구 제외 승인 기준은 실행 전에 manifest에 반드시
설정하며 실행 중 임의 변경하지 않는다. 타임아웃이나 MGF 탈락 하나를 곧바로
악성의 암호학적 증거라고 부르지 않는다. 네트워크 문제·정직한 outlier로 인한
가용성 제외와, 서명된 equivocation 등 검증 가능한 위반에 따른 제재를 구분한다.
영구 제외는 해당 사전 정책과 BFT 승인에 따라 수행한다.

멤버를 영구 제외하거나 그룹을 재편할 때는 그 그룹의 **남은 모든 클라이언트가
새 독립 비밀키를 생성**하고 VSS 및 초기 commitment 연결 증명을 다시 수행한다.
다른 그룹과 합치면 새 그룹에 들어가는 모든 기존 멤버도 새 키를 쓴다. 새 키의
검증된 share와 등록 인증서가 준비될 때까지 영향받은 그룹은 참여하지 않는다.
준비된 다른 그룹은 계속 진행할 수 있다. 키 교체 인증서는 VSS의 유효한 복원
정족수가 준비됐음을 확인한 뒤 효력을 갖는다.

**같은 비밀키의 Shamir share만 새로 만드는 작업은 키 합 누출의 해법이 아니다.**
키를 바꿔도 이미 공개된 옛 키나 옛 업데이트를 되돌려 숨길 수는 없다. ledger는
옛 key epoch까지 보존한다. 서로 다른 그룹의 key epoch가 달라도 HPRF의 round/
block 입력은 같게 유지하고, epoch는 commitment·증명·ledger에서 식별한다(§3).

부분 진행은 전역 중단을 줄일 뿐 무조건적인 liveness를 보장하지 않는다. 모든
그룹이 방해받거나 VSS/BFT 정족수가 없으면 진행할 수 없다. 그룹 단위 탈락은
MGF를 통과한 정직한 업데이트도 제외하므로 원본 개별 필터와의 차이·정확도·
지연·재공유 빈도를 측정한다. 이 그룹 처리 절차 자체를 CCS/VRF 구현으로 표시하지 않는다.

## 3. HPRF 입력 인코딩 계약

### 3.1 충돌 없는 round/block 인코딩

원본 `aion_original_hprf.py`는 `x + block`을 사용한다. 따라서 같은 client/key의
round `r`, block `c`와 round `r+1`, block `c-1`은 `c >= 1`에서 같은 입력을
갖는다. 비교 가능한 전송 좌표에서 마스크가 재사용되면 업데이트 차이에 대한
관측이 가능하다. 모든 round의 전체 벡터가 동일하다는 뜻은 아니다.

새 profile은 다음 값을 manifest와 HPRF 파라미터에 고정한다.

```text
1 <= round <= round_max < 2**round_bits
0 <= block < blocks_max <= 2**block_bits
input_bits = round_bits + block_bits
Encode(round, block) = I2B(round, round_bits) || I2B(block, block_bits)
```

`I2B`는 big-endian 고정 폭 비트열이며 선행 0을 보존한다. 비트열의 MSB부터
해당 HPRF의 명시된 행렬 곱 규칙에 따라 처리한다. 정수 표현으로는
`(round << block_bits) | block`과 같다. 범위 초과는 거부하고, 덧셈 `r+c`,
truncation, 짧은 hash, 입력 정수의 `mod q`로 대체하지 않는다. 이 계약은
허용 범위에서 서로 다른 `(round, block)`의 **인코딩 충돌**을 배제한다.
서로 다른 입력의 PRF 출력 충돌 확률을 0으로 만든다는 뜻은 아니다.

폭은 지원할 최대 round/모델 블록 수를 기준으로 사전에 선택한다. 입력 비트 수는
BLMR의 보안 조건과 공개 행렬 계산 비용에 영향을 주므로 임의의 64+64비트를
붙인 뒤 보안 파라미터를 그대로 재사용하지 않는다. 모델 flatten 순서, 블록
출력 길이, 마지막 블록 잘라내기 규칙도 고정한다.

기존 `numeric.py`의 별도 LWE 연구 profile에는 64+64비트 연결이 이미 있지만,
그 사실은 원본 scalar profile의 `r+c`가 수정됐거나 보안 파라미터가 검증됐다는
뜻이 아니다. 기존 artifact는 변경하지 않고 새 profile에서 새 계약을 사용한다.

### 3.2 task, 재시도, key epoch

새 task는 새로운 독립 client 키로 시작한다. 서로 다른 task에서 키를 재사용하지
않는다. task/setup/profile ID, 모델/manifest hash, client ID, key epoch는
commitment와 ZKP의 공개 맥락에 바인딩한다. 이 task별 새 키 규칙이 교차 task
마스크 재사용을 막는 전제다. task 사이 키 재사용은 이 profile의 지원 범위 밖이다.

같은 집계에 포함되는 모든 client와 ASR aggregate HPRF 호출은 **같은 입력**을
사용해야 한다. client ID, client별 key epoch 또는 그룹 ID를 HPRF 입력에 각각
넣으면 단일 `H(sum k_i, input)` 복원이 성립하지 않는다. 이 정보는 증명의
맥락에 넣는다. 향후 보류한 그룹 재등록을 도입한다면 입력이 아니라 비밀키
자체를 새로 만들어야 한다. 현재 task 안의 자동 그룹 재등록은 구현 범위 밖이다.

클라이언트도 `(key_epoch, round)`의 제출 vector digest를 영속화한다. 같은
round의 재시도에서 새로운 학습 업데이트를 같은 마스크로 보내지 않는다.
업데이트·모델·bound를 바꾸거나 새 후보를 제출하려면 새로운 round ID를 쓴다.
건너뛴/실패한 round ID도 재사용하지 않는다. 공개 point `r+c` 대신 비트열을
사용해도 기존 scalar 함수를 BLMR로 바꾼 것이 되지는 않는다.

## 4. 모듈러스·오차·범위 조건

혼동을 막기 위해 네 공간을 구분한다.

| 기호 | 의미 | 계약 |
| --- | --- | --- |
| `p` | HPRF 출력과 update 집계의 모듈러 정수 공간 | `Z_p`; 집계 산술 자체는 소수성을 요구하지 않음 |
| `q` | HPRF 키/내부 선형 연산 모듈러스 | 선택한 구성에서 `q > p`와 키·행렬·반올림 조건 확인 |
| `ell` | Pedersen 군의 소수 위수, VSS scalar 체 | 정수 합 보존을 위한 아래 no-wrap 조건 |
| `P_zk` | 증명 회로의 체 모듈러스 | 연산의 정수 의미를 별도 범위/limb 제약으로 보존 |

### 4.1 VSS와 키 합

새 profile의 기본 계약은 각 key 좌표를 `0 <= k_ij < q`로 증명하고,

```text
ell > N_max * (q - 1)
```

을 강제하는 것이다. `ell > N_max*q`도 더 보수적인 충분조건이다. VSS가 복원한
값은 좌표별 정수 합이고, 이 값을 `mod q`로 바꿔 HPRF에 넣는다. 현재 2048비트
곱셈 군의 위수 ORDER가 임의의 새 q에도 충분하다고 가정하지 않는다.

소수 q 위에서 직접 VSS를 하는 대안은 여기의 기본 계약이 아니다. 그 대안을
택하면 commitment 군의 위수·키 범위·복원식을 함께 다시 정해야 한다.
보류한 누출 검사를 나중에 추가할 경우 그 검사 체도 함께 검토해야 한다.

### 4.2 ASR의 오차와 용량

공통 선형 평가 후 마지막에 한 번 round-to-nearest를 하는 정확한 구성이라면,
N개 개별 반올림과 한 번의 aggregate 반올림으로 좌표별 정수 오차에 대해
`|e| <= (N+1)/2`라는 충분 상한을 얻는다. 기본 보수 상한은 다음과 같다.

```text
E_max = ceil((N_max + 1) / 2)
Delta > 2 * E_max
|z_ij| <= B_z
1 <= n_i <= n_max
sum_{i in A} n_i <= W_max
p > 2 * (Delta * B_z * W_max + E_max)
```

이는 해당 반올림 구조의 상한이지 임의의 LWE HPRF에 자동 적용되는 값이 아니다.
추가 noise, 중간 반올림 또는 다른 rounding 규칙을 사용하는 구성은 E를 다시
유도한다. ASR은 키 share를 먼저 정확히 복원하고 HPRF를 한 번 평가하므로,
HPRF 출력을 라그랑주 보간하는 AMR의 오차 증폭식을 사용하지 않는다.

BLMR canonical mask는 `0 <= h_ij < p`로 고정한다. 원본 adapter의 raw 출력은
p가 될 수 있으므로 그 결과와 구분한다. MGF의 alpha·hmax·대표값 규칙도 동일한
profile로 고정한다. n_i의 상한만으로 데이터 개수를 증명한 것은 아니며,
실험에서는 승인된 데이터 분할 가중치와의 일치도 확인한다.

### 4.3 HPRF 보안과 증명 체

`q > p` 또는 큰 `q/p`만으로 HPRF 보안이 성립하지 않는다. 인용한 BLMR §5는
LWE 차원 n과 실제 키 폭 m을 구분하며 `m = n*ceil(log2(q))` 형태와 입력 길이,
공개 행렬 분포 및 잡음 조건을 요구한다. **키 폭을 512~1024로 미리 확정하지 않는다.**
Ring-LWE 구성은 기본 BLMR 벡터/행렬 구성의 단순 이름 변경이 아니다.

`trustlessfl/lwe_parameters.py`의 필요 형태/충분조건 검사를 재사용한다. 그 검사
통과도 보안 증명은 아니다. Lattice Estimator에는 실제 차원, modulus, secret/
error 분포, 샘플 수와 공격 비용 모델을 입력하고 버전·입력·결과를 기록한다.
estimator는 알려진 격자 공격 비용을 휴리스틱하게 추정하는 도구이지 HPRF의
환원 조건, related-key/aggregate-key 노출 또는 전체 프로토콜 안전성의 검증기가 아니다.

`q < P_zk`만으로 회로가 안전하지 않다. 일반 공개 계수 내적의 정수 상한은
예를 들어 `d_k*(q-1)**2`까지 될 수 있고, 스케일링·norm 제곱합도 별도 상한이
필요하다. 각 정수 등식의 차이가 P_zk의 배수로 바뀌어 통과하지 못하도록
range/quotient/remainder를 제약한다. 중간값이 크면 다중 limb 산술을 사용한다.
반대로 q가 P_zk보다 크다는 이유만으로 구현 불가능한 것은 아니다.
증명 체 크기에 억지로 맞추려고 HPRF 보안 파라미터를 약하게 줄이지 않는다.

수치 toy profile은 먼저 실행할 수 있지만, 구체 파라미터·분포·입력 길이·성능
평가가 끝나기 전에는 새 profile을 보안 검증된 BLMR/production-secure라고
표시하지 않는다. 작은 scalar key의 기존 성공 결과도 새 profile의 보안 근거가 아니다.

## 5. 벡터 키 공유와 commitment 연결의 비용

기본 구현은 키 좌표마다 기존 Pedersen VSS를 적용하고 메시지는 묶는다.
일반적인 PRG로 짧은 시드를 벡터 키로 확장하면
`PRG(sum(seed_i)) == sum(PRG(seed_i))`가 성립하지 않는다. 따라서 짧은 시드만
공유하는 방식을 ASR의 대체로 사용하지 않는다. 별도 homomorphic 압축/packed VSS는
새 안전성·복원 검토가 필요한 별도 설계이며 현재 비용 계산에 포함하지 않는다.

`d_k`를 실제 key 좌표 수, `a`를 share 수신 집계자 수, `t_vss`를 복원 threshold,
`b_ell`을 scalar 바이트 수, `b_G`를 commitment 군 원소 바이트 수라고 하면:

- 클라이언트 1명의 초기 Pedersen share payload: 약 `2*a*d_k*b_ell` 바이트.
  각 좌표의 secret share와 blinding share를 모두 센다.
- 초기 commitment: `t_vss*d_k`개, 약 `t_vss*d_k*b_G` 바이트.
  이는 한 번 게시해 재사용할 때의 수치다. 수신자별 envelope에 복제하면 전송량은
  더 크다. 암호화·서명·ZKP·메타데이터 오버헤드도 별도 계상한다.
- 매 round의 ASR aggregate-share payload도 응답 집계자당 약 `2*d_k*b_ell`이다.
  이것은 저장된 초기 shares를 합친 **집계자 응답**이지 client의 새 mask sharing이 아니다.
- 초기 연결 증명은 벡터 키 전체와 모든 필요한 VSS commitment에 결속해야 한다.
  Poseidon commitment 하나로 요약해도 최초 연결의 연산량이 공짜가 되지는 않는다.
- 향후 그룹 키 교체를 도입한다면 영향받은 client들의 초기 공유·연결 증명 비용이
  다시 발생한다. 현재 구현 일정에는 그 보류 비용을 포함하지 않는다.

예를 들어 현재와 같은 256-byte scalar/군 원소 표현, d_k=512, a=4,
t_vss=2라는 **비용 산술 예시**에서는 client당 share payload가 1 MiB,
commitment가 256 KiB다(중복·봉투·증명 제외). 이 d_k=512를 안전한 BLMR
파라미터로 승인한 것이 아니다. 대규모 파라미터에서는 훨씬 커질 수 있다.

## 6. 수치 기준 구현의 진입/완료 조건

정책·입력 형식·조건은 위 계약을 따른다. 구체 HPRF 보안 파라미터와 회로 backend는
여전히 선정 과제다. 초기 share와 round별 ASR·ZKP 비용을 보고한다.
아래 시험을 통과하기 전 새 Flower 경로를 기본값으로 바꾸지 않는다.

진행 순서는 [재검토 §6](reproduction/asr-plan-feasibility-2026-10-06.md)의
수치/CCS 기준 시험 → 실제 HPRF·VSS 비용 → 완전한 ZKP 소형/전체 모델 시험 →
Flower 연결 → 1/4/10-round 학습 검증이다. CCS 등록·난수와 초기 VSS 연결 증명
비용은 확인한다. 공개 이력 검사·all-or-none 정책 비교·그룹 키 교체 시험은
진입 조건에서 제외한다. 다음은 현재 각 단계가 공유하는 시험 목록이다.

1. 허용 범위의 round/block 인코딩 injectivity, 선행 0, 경계/초과 거부,
   원본 `r+c` 충돌 fixture, 다른 client의 공통 입력, task/재시도 상태 검증.
2. 양·음 업데이트, mask carry, 작은 반올림 오차, 가중치, center 경계,
   VSS no-wrap 경계의 양자화 평문 대조군 비교. 설정·범위·증명 검증 실패는
   share 공개 전에 거부한다. 실패/재시작해도 해당 round의 제출·확정 기록을 지우고
   다른 명단/업데이트를 같은 round로 재발급하지 않는다.
3. VRF test vector·공개키/증명 검증, 등록 이후 키 바꿔치기·다른 task의 증명 재사용,
   CCS subset 자격·제출 시한, 개별 필터링, 최소 인원, BFT 명단 결속 및 재시도 회귀.
4. 초기 VSS/증명 commitment 바꿔치기, 틀린 HPRF/mask, Delta 이동,
   범위 밖 update·가중치·회로 wrap, 다른 모델/bound/round의 증명 재사용 거부.
5. 작은 차원의 **완전한** 연결 증명부터 전체 차원까지 생성·검증 시간, peak RAM,
   proof/wire bytes, 초기 VSS 비용 측정. norm만 증명한 결과를 전체로 외삽하지 않음.
6. Flower의 BFT① 승인과 aggregate-share 발급 순서, BFT②의 모델·MGF 이력
   재검증. 숫자 정확성을 학습 정확도·전체 liveness·production 보안과 구분.

## 이번 문서 작업의 확인 범위

문서 작성 중 일회성 Python assertion으로 다음을 대조했다. 새 런타임·ZKP
시험이나 전체 저장소 회귀 실행이 아니며, 보안 검증된 HPRF 시험도 아니다.

- 로드한 원본 HPRF의 key 31337에서 round 4/block 1과 round 5/block 0의
  raw mask 512/512좌표가 동일함을 확인했다. 원본 코드는 수정하지 않았다.
- 3-bit round/4-bit block toy 인코딩의 112개 입력이 서로 다르고, 위 형태의
  덧셈 충돌을 분리하며, 네 가지 범위 밖 입력을 거부하는 것을 확인했다.
- F_101 위의 차분·삼각형·고정 그룹·공모 키 제거 사례 다섯 개를 확인했다.
- 보안성이 없는 rounded-linear toy(`p=101`, `q=1009`, 공개 계수 913,
  `Delta=8`, 두 키 각각 0..19, update 각각 -1..1, 가중치 (1,1)/(2,3))의
  7,200건에서 center/round 복원이 정확했다. 400개 키 쌍 중 206개에 mask
  wrap이 있었고 최대 작은 오차는 1이었다. 이 값은 실제 BLMR 파라미터가 아니다.
- 벡터 공유 비용 예시의 1 MiB/256 KiB 계산과 새 문서의 로컬 링크를 확인했다.
