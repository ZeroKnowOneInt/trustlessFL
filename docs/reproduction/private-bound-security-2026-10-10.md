# MPC 실행 전 아이디어 보안 검토

날짜: 2026-10-10. 브랜치: `work/aion-private-bound-no-wrap`.

**판정: no-wrap 정수 산술은 유지할 가치가 있지만, 현재 필터 출력 정책과 평균 기반 동적 경계는 그대로 채택할 수 없다. MPC를 정확하게 실행해도 아래 반례의 출력이 나온다.**

이번 검토는 TLS와 네트워크 공격을 제외하고, 이상적으로 안전한 MPC가 지정된 함수를 정확히 계산한다고 가정한다. native MPC·FMNIST 학습을 새로 실행하지 않았다. 합성 정수 입력으로 공개 함수 자체의 누출과 robustness 한계를 검증했다. 보안 승인을 의미하지 않는다.

실행 코드: [`audit_private_bound_security.py`](../../experiments/audit_private_bound_security.py).
기계 판독 결과: [`private-bound-security-results.json`](private-bound-security-results.json).

## 1. 무엇을 보호하려는가

현재 함수는 각 client의 정수 업데이트 u를 비밀리에 복원하고, 좌표 상한과 격자 검사를 통과한 경우 `e_i = [||u_i||² <= T]`를 계산한다. 최종 출력은 `status`, `a=sum(e_i)`, `U=sum(e_i*u_i)`다. 입력 key, raw offset, 개별 norm, e_i 자체를 직접 공개하지 않는 것은 바람직하다.

그러나 공개된 함수 결과에서 역으로 유도할 수 있는 정보는 MPC가 숨기지 못한다. `비밀 e_i`는 `e_i에 관한 정보가 전혀 없다`와 다르다. 최소 통과 인원 2명은 정상 통과 인원 2명을 뜻하지 않는다.

[Aion 원문](https://www.usenix.org/system/files/usenixsecurity25-liu-yizhong.pdf)의 §3.2 및 §8 Figure 10은 라운드 q명 중 q−2 클라이언트 공모를 다루며, 고정 online 명단의 honest 업데이트 합을 기준 공개 정보로 둔다. 부록 A는 공통 모델에 대한 BFT 인증도 요구한다. 따라서 새 함수가 추가한 선택·count·abort·반복 출력의 공개 계약을 다시 정의해야 한다. 원논문의 증명이 자동으로 이전되지 않는다. 이 검토는 원논문 자체나 선택 후 합을 명시한 모든 MPC 기능이 깨진다고 주장하지 않는다.

정상 클라이언트라도 로컬 학습 결과가 동적 T를 넘을 수 있다. 현재 encoding은 |u_j|<=B만 강제하고 모든 정상 입력의 norm<=T를 보장하지 않는다. 아래 사례를 배제하려면 모든 정상 입력이 항상 통과한다는 별도의 강한 가정과 근거가 필요하다.

## 2. 한 번의 출력으로 정상 업데이트가 노출된다

q=4, 좌표 상한 B=10, 제곱 norm 경계 T=25, 최소 통과 인원 2명으로 둔다. 공격자 둘의 업데이트는 0,0이고 정상 둘은 3,6이다.

| 입력 | 제곱 norm | 통과 |
|---|---:|---|
| 공격자 1: 0 | 0 | 예 |
| 공격자 2: 0 | 0 | 예 |
| 정상 1: 3 | 9 | 예 |
| 정상 2: 6 | 36 | 아니오 |

함수는 `count=3, SUM=3`을 출력한다. 공모자의 기여 0을 제거하면 통과한 정상 한 명의 업데이트값 3이 그대로 남는다. 출력만으로 어느 정상 client의 값인지 항상 식별되는 것은 아니다. 다른 정상 client의 탈락을 추가 정보로 아는 경우에는 identity까지 연결할 수 있다. 서버가 개별 masked upload에서 unmask한 것이 아니며, 공개 합이 개인 업데이트와 같아진 것이다.

더 엄밀하게, 정상 입력 `(3,6)`과 `(1,8)`은 필터 전 합이 모두 9이고 공격자 입력도 동일하다. 하지만 선택 후 출력은 각각 `(SUM=3,count=3)`과 `(SUM=1,count=3)`으로 다르다. 따라서 같은 online 명단의 필터 전 합만으로 이 새 출력을 재현할 수 없다. count를 숨겨도 이 두 세계의 SUM 차이는 남는다.

`mean-only`도 원래 공개 합만의 프라이버시를 일반적으로 복원하지 않는다. B=20, T=64에서 정상 입력 `(6,12)`와 `(3,15)`는 원래 합이 모두 18이다. 공격자 입력은 0,0이며, 각각 정상 6 또는 3만 통과해 공개 정수 평균이 2와 1로 달라진다. count를 공개하지 않아도 동일한 원래 합을 가진 두 세계가 구별된다. 다만 RoundEven된 평균은 일반적으로 정밀도를 잃으므로 평균에 인원수를 곱하면 언제나 정확한 개인 업데이트를 복원한다는 주장은 하지 않는다.

## 3. 같은 입력을 재사용하면 여러 정상 업데이트를 분리할 수 있다

### 경계값을 바꾼 두 번의 집계

고정된 입력 `0,0,3,6`에 대해:

- T=36: `count=4, SUM=9`.
- T=9: `count=3, SUM=3`.

두 결과로 정상 업데이트의 벡터값 3과 6을 얻는다. 추가 정보 없이 두 client identity에 어느 값을 배치할지는 결정되지 않을 수 있다. 매 실행의 key/mask를 새로 생성해도 같은 업데이트를 다시 집계하면 SUM 관계는 같다. 현재 reference API와 native fixture에는 이런 재질의를 막는 영속 ledger가 없다.

### 명단을 바꾼 두 번의 집계

공격자 0 및 정상 입력 1,2,3을 모두 집계하면 SUM=6이다. 정상 1만 빠진 명단을 다시 집계하면 SUM=5이다. 차이 1이 해당 정상 업데이트다. 각 공개 합에는 정상 기여자가 각각 3명과 2명 있어도 재사용이 허용되면 누출된다.

이 공격의 조건은 같은 frozen 업데이트의 재사용이다. 정상적으로 새 모델에서 새 업데이트를 만든 서로 다른 라운드의 차이가 언제나 개인 업데이트를 뜻한다는 주장은 아니다.

## 4. 합계 평균 norm으로 경계를 갱신하는 정책은 공격에 취약하다

현재 갱신은 공개 정수 평균 g의 제곱 norm Q로 다음을 계산한다.

```
eta = clip((Q_new+1)/(Q_old+1), 1/4, 4)
T_next = clip(RoundEven(T_previous*eta), T_min, T_max)
```

B=10, 초기 T=100, T_min=1, T_max=100의 실제 갱신 함수로 다음을 재현했다.

| 라운드 | 입력 | 출력 평균 | 다음 경계에 미치는 결과 |
|---|---|---:|---|
| 1 | 10,10,10,10 | 10 | Q_old=100 |
| 2 | 공격자 −10,−10 / 정상 10,10 | 0 | Q_new=0, T가 100→25 |
| 3 | 공격자 0,0 / 정상 10,10 | 0 | 정상 둘 탈락, 공격자 둘만 통과 |

라운드 2의 모든 업데이트는 현재 경계를 준수한다. wrap 오류나 잘못된 마스크가 없어도 공격자는 평균을 상쇄해 다음 경계를 낮출 수 있다. 라운드 3은 `count=2`를 만족해 성공으로 처리되고, 다음 T도 25로 유지된다.

**공격자가 없어도 문제가 가능하다.** 정상 클라이언트만 있고, 첫 평균이 10이었다가 다음 업데이트가 `10,−10,10,−10`이면 평균이 0으로 상쇄된다. 다음 T=25에서 같은 정상 업데이트 전부가 탈락한다. abort가 성공 history를 바꾸지 않는 현재 정책에서는 동일한 상황이 이어지면 임계값도 25에 머문다. 이것은 합성 반례이며 기존 FMNIST pilot에서 실제 발생했다는 의미가 아니다.

원인은 `||mean(u_i)||²`가 개별 `||u_i||²`의 규모를 나타내지 않는다는 점이다. 이 값으로 개별 입력의 허용 경계를 갱신하는 현재 식은 폐기하거나 목적을 바꿔야 한다. 단순한 ratio clipping이나 작은 floor로 일반적으로 해결되지 않는다.

## 5. L2 제한은 학습의 정직성을 증명하지 않는다

20명 중 정상 둘이 +1, 악성 18명이 −1을 보내면 모든 제곱 norm은 1이다. T=1에서는 전부 통과하고 SUM=−16으로 정상 방향과 반대가 된다. 이는 방향 반전 합성 사례이며 실제 FMNIST backdoor 성능 측정은 아니다.

Aion의 q−2 공모 허용은 프라이버시를 위한 공격자 능력과 관련된다. 이 수치로 악성 클라이언트가 거의 전부인 경우의 학습 정확도까지 보장된다고 해석해서는 안 된다. 정확한 범위 검사와 악성 참여자에 안전한 MPC도 `허용 범위 안의 악성 학습 입력`을 정상 학습으로 바꾸지 못한다. 별도의 poisoning 가정·기준·평가가 필요하다.

## 6. no-wrap와 Large M의 판단은 분리해서 유지한다

raw offset을 비밀 입력하고 마스크를 개별 제거한 뒤, full quotient의 격자·상한을 검사하고 invalid 좌표를 sanitize하면 정수 의미의 wrap 회피는 유효하다. 최종 SUM을 modulo M으로 되돌리지 않으므로 M보다 큰 정수 합을 처리할 수 있다.

이번 추가 검사는 4개 M(1,15,840000021,2^128) × d(1,21)에서 독립 정수 oracle과 **3,118개 wire/range 사례**를 비교했다. 작은 M에서는 선택한 마스크 대표값별 가능한 wire word를 모두 검사했고, 큰 M에서는 valid 입력과 경계값을 검사했다. 모두 일치했다. 기존 원본 HPRF adapter 산술 감사도 재실행하여 **64,000 좌표 합**이 일치했다. native finite-field 회로를 새로 실행하거나 암호 보안을 증명한 결과는 아니다.

M=1을 허용하려면 raw Y까지 비공개여야 한다. 예를 들어 d=21, Y=21u+m, m∈{0,1}이면 `floor(Y/21)=u`다. 공개 Y에서 키 없이 42개 음수·양수 입력/마스크 조합이 모두 복원됐다. 이것은 raw Y를 공개하는 잘못된 통합의 위험이며, 제안한 비밀 입력 경로가 raw Y를 공개한다는 뜻은 아니다. Flower의 기존 공개 masked-vector 경로에 작은 M만 적용해서는 안 된다.

Large M 때문에 norm이 mask에 지배되는 문제는 개별 unmask 후 검사함으로써 피할 수 있다. 기존 큰 M을 유지하면 입력 폭과 scaling 비용은 남는다. 원래 Aion의 단일 aggregate-mask 효율을 보존하는 증명도 아니다.

## 7. 어떤 수정이 먼저 필요한가

### 출력 계약과 공모 상한

클라이언트 공모 상한을 t_C로 고정하고, 성공 출력에 정상 기여자 최소 h_min명을 요구한다면 총 통과 인원 조건은 `a >= t_C+h_min`이어야 한다. 이는 등록된 distinct identity와 실제 공모 상한을 전제로 한 최악의 경우 하한이다. 9,425개의 소규모 인원 조합으로 하한을 검증했다. 익명 ID 개수를 늘리는 것은 Sybil 방어가 아니다.

t_C=q−2, h_min=2이면 a>=q여서 한 명이라도 제외하면 성공 출력을 낼 수 없다. 강한 공모 모델 아래에서 임의의 개인 탈락과 유용한 정확한 합 공개를 모두 얻겠다는 현재 기대에는 충돌이 있다. 이 counting guard는 원래 ideal functionality나 differential privacy를 복원하는 충분조건이 아니다. `정상 둘이 포함됨`도 공개 합과 외부 정보가 우연히 개인을 결정하는 모든 경우를 막는 보장이 아니다.

또 all-pass에서만 출력하도록 바꿔도 `(3,6)`과 `(4,5)`는 같은 원래 합 9를 가지지만 T=25에서 각각 abort/ok가 된다. **abort도 입력 의존 공개 정보**로 새 보안 계약에 포함해야 한다. 실패 후 T나 명단을 바꿔 같은 입력을 다시 조회해서는 안 된다.

### 동적 경계

공개 평균 norm 기반 자동 갱신을 다음 MPC 학습 실험의 기본값으로 사용하지 않는다. 검증 단계에서는 공격자가 조작하기 어려운 별도 calibration에서 사전 확정한 T를 사용한다. 고정 T는 동적 상쇄 공격의 경로를 줄일 뿐, 선택 후 누출이나 norm 안의 공격을 해결하지 않는다.

적응형 경계가 필요하면 개별 norm들의 분포를 MPC 내부에서 계산하는 정책을 별도로 검증한다. median/quantile도 악성 비율 가정이 필요하며 q−2 공모 환경에서 일반적인 robustness를 보장하지 않는다. 추가 통계의 공개, 이 통계로 바뀐 다음 출력·abort의 누출, 소수 집단 탈락을 새 이상 기능에 반영해야 한다. 여기서는 대안 정책을 구현하거나 안전하다고 판정하지 않았다.

### 라운드·명단·모델·입력 결속

입력 전 `epoch, logical_round, model_hash, fixed_roster, policy_hash, circuit_hash, previous_output_certificate`를 합의하고 인증한다. client는 같은 모델/정책을 확인한 뒤 한 번만 입력한다. 각 honest aggregator와 client가 영속 상태로 frozen 입력의 새 정책/새 명단 재사용을 거부해야 한다. 단순 UUID나 nonce 추가만으로 이 조건을 만족하지 않는다.

영속 상태는 성공뿐 아니라 입력 소비와 abort도 다뤄야 하며, 공개 후에는 새 session 이름으로 다시 집계할 수 없어야 한다. 동일 실행의 전송 재시도와 동일 입력에 대한 새 질의는 구분한다. 분산 인증서·ledger는 현재 native fixture에 구현되어 있지 않다.

### Aion과의 연결 및 보장 범위

현재 native key는 매 실행 client가 제공한다. 기존 Aion VSS에 등록된 key와의 결속을 import/검증하는 경로가 없다. 내부 계산상 key와 offset이 일치한다는 사실은 기존 등록 key와 동일하다는 증명이 아니다. 입력 인증·최종 output 인증서·공통 모델 확인·MPC 프로그램/정책 합의는 따로 구현해야 한다.

MPC 프로토콜의 악성 참여자 보장은 정상 실행의 계산 정확성/프라이버시와 abort를 다루며, 그것만으로 Aion의 BFT 진행성·동적 참여·비동기 모델 사용이 이전되지 않는다. 클라이언트 dropout과 악성 abort의 처리도 남아 있다. 네트워크/TLS 점검은 이러한 구현 검토의 별도 항목이며, 위 1–6절의 반례에는 필요하지 않다. 기존 로컬 TLS fixture를 적대적 네트워크에서의 인증 보안 검증으로 해석하지 않는다.
