# ASR·비공개 MGF 후속 계획의 실현 가능성 재검토

검토일: 2026-10-06. 범위: 원문·현행 코드 읽기, 기존 파라미터 검사 시험,
정수 용량 및 통신량·그룹 생존 확률 계산. **새 HPRF, VRF, ZKP 또는 Flower
런타임을 구현하거나 성능 측정한 보고서가 아니다.**

후속 사용자 결정: **참여 정책은 CCS/VRF까지 진행**한다. 공개 이력 rank 검사,
all-or-none 그룹 처리, 관련 그룹 재편·키 재공유는 이번 구현·완료 조건에서 뺀다.
아래 수치 감사는 보존하며, §4 정책 비교는 보류 기록이다. §6은 이 결정을 반영한 현재 계획이다.

## 1. 결론과 유지할 목표

모듈러 복원으로 carry를 제거하는 산술 계약은 유지한다. 그러나 전체 구성이
현재 장비에서 실용적이라는 결론은 아직 낼 수 없다. BLMR·최초 VSS 연결 증명의
비용과 CCS/VRF 등록·난수 조건을 먼저 검증해야 한다. 기존 all-or-none 그룹 및
공개 이력 누출 검사 보강은 사용자 결정으로 이번 범위에서 제외한다.

- Flower 메시지 전달, ASR, 클라이언트 로컬 학습·마스킹을 유지한다.
- 추가 좌표별 carry/마스크 share, 개별 평문 또는 MGF 벡터 공개를 해법으로 쓰지 않는다.
- MGF는 원본의 masked norm 조건을 비공개로 증명한다. 직접 update norm으로 바꾸지 않는다.
- 키는 task 초기 한 번 공유한다. 누출 대응을 위한 그룹 재등록은 이번에 넣지 않는다.
  같은 키를 재사용하는 다중 라운드의 명단 변동으로 개인 키가 노출될 수 있음을 명시한다.
- 원본 재현 profile은 보존한다. 새 구성은 **Aion-ASR 기반 확장**이며 원본과
  동일한 wire, 초기 percentile, 임계값 이력이라고 표시하지 않는다.

상세 산술·입력·범위 계약은 [설계 문서](../asr-modular-private-mgf-design.md)에 있다.

## 2. 수치 용량은 성립하는 예가 있다

```text
N_max = 100, B_z = 10^7, W_max = 60,000
E = ceil((N_max + 1)/2) = 51, Delta = 256
p = 2^49 = 562,949,953,421,312
2*(Delta*B_z*W_max + E) = 307,200,000,000,102 < p
Delta = 256 > 2*E = 102
```

따라서 해당 범위의 입력과 마지막 nearest-rounding 구조에서는 centered 복원과
오차 흡수가 가능하다. 이 예는 출력 모듈러스의 용량 확인이지 HPRF 보안 파라미터
승인이 아니다. `S=10^6`이라면 같은 입력·가중치에 대한 nearest 양자화 평균의
좌표 오차는 최대 `1/(2*S)`다. clipping의 영향이나 장기 학습 정확도는 별도다.

## 3. BLMR·벡터 VSS의 비용을 과소평가하면 안 된다

[BLMR §5](https://crypto.stanford.edu/~klewi/papers/homprf-proc.pdf)의 기본 구성은
키 폭 `m = n*ceil(log2(q))`인 벡터와 `m*m` 공개 행렬을 사용한다. 현재의
[검사 도구](../../trustlessfl/lwe_parameters.py)는 다음 두 조건의 공통 구간을 계산한다.

```text
alpha * m^L * p <= 2^(-target_bits)   # 정리의 negligible 조건에 대한 구체 검사값
q > 2*sqrt(n)/alpha                 # 같은 논문이 인용한 Regev 조건
```

`n=128, p=2^49, target_bits=128`을 넣은 계산 결과다. **n=128을 안전한 차원으로
승인한 것이 아니며, target_bits=128도 공격 비용 128비트를 의미하지 않는다.**

| 입력 비트 L | 위 두 검사에 공통 구간이 생기는 q 비트 수 | 키 폭 m | 초기 share/client | 초기 commitment/client |
| --- | ---: | ---: | ---: | ---: |
| 7 | 288 | 36,864 | 72 MiB | 18 MiB |
| 8 | 304 | 38,912 | 76 MiB | 19 MiB |
| 16 | 434 | 55,552 | 108.5 MiB | 27.125 MiB |
| 32 | 709 | 90,752 | 177.25 MiB | 44.3125 MiB |

7비트의 예는 최대 60라운드를 위한 round 6비트와 61,706좌표를 채우는 두 블록의
block 1비트를 합친 것이다. 실패·건너뛴 round도 ID를 소비하므로 60개의 성공한
round를 보장하는 설정은 아니다. 더 큰 모델/round 수에는 입력 폭부터 재검사한다.

share는 기존 256-byte scalar 표현, 집계자 4명, secret/blind share 각 1개로
`2*4*m*256`을 계산했다. commitment는 threshold 2, 256-byte 군 원소를 가정해
`2*m*256`이다. 봉투·중복·연결 증명은 제외했다. 이 네 예의 q 상한에서는 기존
VSS 위수에 대한 `ell > 100*(q-1)` 조건도 만족한다.

한 입력의 행렬 곱을 q 크기의 정수로 조밀하게 저장하면 L=7 예에서 약 45.56 GiB다.
이것은 **단순 저장 방식의 비용이지 메모리 하한이 아니다**. 낮은 norm을 이용한
압축, 순차 행렬-벡터 연산 또는 streaming으로 줄일 수 있으나 시간·증명 비용을
측정해야 한다. 이 검토 환경의 물리 RAM은 약 15 GiB다.

이 표는 가능한 모든 HPRF의 최소 비용이나 구현 불가능성 증명이 아니다.
q 비트 수 검색은 각 길이의 최대 정수로 부등식을 검사했을 뿐, 실제 q·alpha·
행렬 분포를 선택하거나 Lattice Estimator를 실행한 것이 아니다. 별도 Ring-LWE/
random-oracle 구성을 채택하면 가정과 증명을 다시 정해야 하며 조용히 대체하지 않는다.

공개 행렬을 미리 계산해도 큰 비밀 벡터와의 내적, 정수 범위, 전체 출력 결속,
초기 VSS commitment 연결의 비용은 남는다. 작은 norm 회로만 측정해서 전체
ZKP가 수 초/수십 초라고 외삽하지 않는다. 현재 실제 prover 측정값은 없다.

## 4. all-or-none 그룹의 가용성 감사 — 현재는 보류한 정책

이 절의 계산과 비교 후보는 이전 검토 기록이다. 아래 정책의 구현·시뮬레이션을
현재 CCS/VRF 구현이나 학습 검증의 선행 조건으로 요구하지 않는다.

정확한 조합 계산의 가정은 다음과 같다.

- 등록 500명 중 악성 100명, 정직 400명.
- 크기 g의 균등 무작위 고정 그룹으로 나누고 완전한 그룹 단위로 100명을 예약.
- 악성은 모두 MGF 탈락, 정직은 모두 통과하고 온라인.
- 멤버 하나라도 탈락하면 그룹 전체를 제외.

한 그룹이 남을 확률은 `comb(400,g)/comb(500,g)`이고, 예약 100명 중 남는 인원의
기댓값은 그 확률의 100배다. 그룹 간 독립성 가정은 이 기댓값 계산에 필요하지 않다.

| 그룹 크기 | 예약 100명 중 남는 인원 기댓값 |
| ---: | ---: |
| 2 | 63.97 |
| 5 | 32.60 |
| 10 | 10.50 |
| 20 | 1.05 |
| 50 | 0.000736 |

이는 학습 측정 결과가 아니며, 크기가 불균등한 실제 `VRF_output mod K` 그룹의
정확한 시뮬레이션도 아니다. 그런데도 완전 그룹만 허용하는 정책의 비용을 드러낸다.
작은 그룹은 가용성을 개선하지만 공모 저항을 자동 보장하지 않는다. 예를 들어
전역 100명 공모 상한만으로 매 그룹에 정직한 키 두 개를 확실히 남기려면
그룹 크기 102 이상이라는 충분조건이 필요해 위 100명 참여 설정과 맞지 않는다.
VRF 배정에 따른 확률적 공모 가정을 쓰려면 그 실패 확률을 별도로 정해야 한다.

당시 제안한 이력 공격·가용성 비교 후보는 다음과 같다. 현재는 모두 보류한다.

1. CCS 배정 안에서 개별 필터링 + 공개 전 선형 누출 검사. 안전한 명단만 공개하며,
   이력이 쌓이면 진행이 멈출 수 있는 기준안이다.
2. 고정 그룹 all-or-none. 이 문서의 보수적 비교군이지 기본값 확정이 아니다.
3. 아직 키 합을 공개한 적 없는 그룹의 최초 통과 명단을 고정하고, 이후 변경에는
   누출 검사/영향받은 그룹의 독립 키 재등록을 적용하는 후보. 첫 공개의 공모 조건과
   이후 키 교체 비용까지 검증해야 하며 해결 완료로 취급하지 않는다.

향후 이 보강을 다시 검토할 경우 MGF 탈락·네트워크 이탈·표적 지연·재가입에 대해
유효 인원, skip 빈도, 재등록 횟수, 공모 가정을 기록한다. 현재는 CCS 자격과 개별
MGF 통과를 기준으로 집계하며, 공개 이력 안전성 검사를 수행했다고 주장하지 않는다.

## 5. CCS/VRF는 포함하되 역할과 등록·난수 조건을 분리한다

[Aion §4.3 Algorithm 4](https://www.usenix.org/system/files/usenixsecurity25-liu-yizhong.pdf)는
초기 모델과 그 threshold signature를 VRF 입력에 사용하고, 결과 `mod K`로
client의 subset을 배정한다. 매 round 무조건 새로 독립 추첨한다는 뜻이 아니다.
VRF 증명은 배정 검증에 쓰이지만, 그 후 dropout/MGF 탈락으로 바뀐 실제 키 합
명단의 차분 관계를 제거하지 않는다. 사용자 결정으로 실제 명단의 공개 이력 누출
검사는 이번에 추가하지 않으며, 해당 위험이 남는 연구용 실행임을 명시한다.

구현 전 다음을 정한다.

- 등록 명단·VRF 공개키·VSS/증명용 commitment를 seed 공개 전에 고정한다.
  seed를 본 뒤 키를 반복 생성하거나 client identity를 늘리는 행위를 막는 등록 가정을 둔다.
- [RFC 9381 ECVRF](https://datatracker.ietf.org/doc/html/rfc9381)의 기존 구현과
  test vector를 사용하고 key validation을 켠다. 서명 hash를 임의로 VRF라고 부르지 않는다.
- BLMR 벡터 키와 Pedersen commitment는 ECVRF의 scalar 키/공개점과 같지 않다.
  별도 VRF 키를 client의 VSS 등록 인증서에 묶는 안을 우선 검토하되, 원본의
  `m_i / Com_0` 직접 재사용과 다른 설계임을 명시한다.
- 현행 [BFT adapter](../../trustlessfl/aion_source_bft.py)는 개별 P-256 commit
  서명들의 목록을 검증한다. 유일한 threshold signature 구현이 아니다. signer subset을
  선택할 수 있는 인증서를 hash한다고 자동으로 편향 불가능한 seed가 되지 않는다.
  seed 생성·유일성·키 등록 순서를 별도 계약으로 확정해야 한다.
- 검증된 난수 원천이 없을 때 고정 seed는 기능 실험에만 사용한다. 이를 공격자 저항
  CCS 완료로 보고하지 않는다. 외부 beacon이나 새 threshold signature는 별도 선택이다.
- 배정 공개 시점과 adaptive corruption 가정을 기록한다. 보류한 all-or-none 검사를
  위해 별도로 전체 멤버십을 조기 공개하는 절차는 이번에 도입하지 않는다.

## 6. 수정한 진행 순서와 통과 조건

| 단계 | 산출물 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 1. 수치·CCS 기준 검증 | 정수 codec/개인 MGF 참조, 입력 인코딩, VRF 생성·검증과 CCS subset 배정 | 양자화 대조군 정확 복원, VRF test vector·자격·키 등록 검증, 개별 필터링과 최소 인원 확인 |
| 2. HPRF·VSS 실측 | 정확한 구성/분포/파라미터 기록, 실제 HPRF 생성·평가 및 초기 VSS benchmark | 정리 조건·알려진 공격 비용 검토와 실제 시간/RAM/바이트 보고; 충분조건만 통과한 후보와 보안 후보 구분 |
| 3. 완전한 ZKP 소형 시험 | 최초 VSS-key 연결, HPRF, C, MGF, 전체 범위·가중치·맥락을 모두 묶는 실제 증명 | 틀린 mask/share-key, Delta 이동, 범위/가중치 위조, replay 거부; 전체 모델 1 client로 확대해 비용 확인 |
| 4. Flower 연결 | CCS 배정 확인 → 증명 확인 → 통과 명단/BFT① → ASR → 모듈러 복원 → 결과/BFT② | 필터 이후 확정 명단과 공개 shares 일치, 동일 round의 제출·확정 기록 보존, 실제 메시지에 개인 평문·carry 없음 |
| 5. 학습 검증 | synthetic 및 FMNIST 정상·공격 실행, 다른 모델 adapter 시험 | 1 → 4 → 10 round 순차 확인; 정확 복원·학습 정확도·방어율·비용·유효 인원을 각각 보고 |

단계 1의 비공개 값 참조 계산은 오프라인 시험 oracle이다. 이를 production wire나
서버의 평문 검증으로 연결하지 않는다. 단계 3의 작은 update 차원이 작은 보안 키를
허용한다는 뜻도 아니다. 축소 파라미터 smoke test는 별도 표시하고, 실제 후보의
전체 key/HPRF/초기 연결 비용을 측정해야 한다. 임의의 비트 폭/비트 추출로 출력
블록을 줄이지 않는다.

CCS 등록·난수 원천 계약과 단계 1의 자격 검증을 통과해야 단계 4를 완료할 수 있다.
증명 backend가 없거나 proof 검증이 실패하면 새 경로는 share를 공개하지 않는다.
mock proof·서명·통과 boolean을 실제 ZKP 완료로 표시하지 않는다.

기존 서명·VSS·BFT 승인·동일 round의 명단 결속은 유지한다. 이번 범위 축소는
미구현 다중 라운드 누출 검사와 대응 정책의 보류이지, 기본 검증을 끄는 변경이 아니다.
키 합 차분 위험은 학습 성공이나 VRF 증명 통과로 해결됐다고 표시하지 않는다.

모델 차원·flatten 규칙·MGF projection·양자화·승인 가중치를 manifest와 adapter로
분리한다. FMNIST 상수를 암호 계층에 박지 않는다. 60-round 재현은 위 비용과
10-round 결과를 본 뒤 필요할 때 진행하며, 장기 실행만으로 보안을 입증하지 않는다.
전체 부분 동기 HotStuff 진행 보장이나 production-security 증명은 이 단계표의
테스트 통과와 별개다.

  해당 예의 VSS no-wrap 조건 확인.
- Python `Fraction(comb(400,g), comb(500,g))`로 §4 조합 확률을 정확 유리수로 계산.
- 원문 BLMR/Aion/RFC 및 현행 BFT 인증서 형식 대조.
- Lattice Estimator, 실제 BLMR 평가, 초기 연결 증명, 실제 ZKP, 새 Flower 학습은
  **이번 검토에서 실행하지 않았다**. 전체 저장소 회귀도 실행하지 않았다.

수치 표의 핵심 재현식:

```python
from math import comb
from fractions import Fraction
from trustlessfl.lwe_parameters import minimum_regev_window_modulus_bits

for bits_in in (7, 8, 16, 32):
    bits_q = minimum_regev_window_modulus_bits(128, 2**49, bits_in, 128)
    m = 128 * bits_q
    print(bits_in, bits_q, m, 2*4*m*256/2**20, 2*m*256/2**20)
for g in (2, 5, 10, 20, 50):
    print(g, float(100 * Fraction(comb(400, g), comb(500, g))))
```
